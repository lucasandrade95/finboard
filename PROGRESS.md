# Progresso

- **2026-09-15** — Multiusuário: cada conta passa a ver só as próprias transações. A migração 6 acrescenta `user_id` em `transactions` (com FK para `users` e índice `(user_id, occurred_on)`) e o repositório ganhou `userId` como primeiro argumento de **todo** método — o filtro entra no `WHERE` também nas escritas, então não existe caminho de leitura ou alteração "global" que alguém esqueça de proteger. Todas as rotas do módulo (listagem, criação, edição, exclusão, categorias, resumo, saldo diário, despesas por categoria, export e import) agora passam pelo preHandler `authenticate` criado na fatia anterior, e o front manda o token em cada chamada. Decisões que valem explicar: (1) mexer numa transação de outra conta responde **404 e não 403** — 403 confirmaria que aquele id existe; (2) o banco antigo, que rodava sem escopo, é **adotado pelo seu único usuário** na migração se houver exatamente um cadastrado; com zero ou vários não há escolha segura, então as linhas ficam sem dono (nada é apagado) em vez de a migração chutar um; (3) a geração de recorrentes no boot passou a rodar **uma vez por dono** (`listOwnersWithRecurring`), senão só uma conta ganharia as cópias do mês; (4) o export deixou de ser uma âncora com `download` e virou fetch + blob, porque âncora não manda header `Authorization`. No SPA, o token vive num store pequeno (memória + `localStorage` + listeners) lido pelo React com `useSyncExternalStore` — assim o mesmo store serve ao `lib/api.ts`, que não é React; sem token o app mostra a tela de login/registro, e um 401 vindo da API descarta o token e limpa o cache do TanStack Query, para os dados da conta anterior não reaparecerem para quem entrar depois na mesma aba. Cinco testes novos no server cobrindo o escopo (listagem, edição/exclusão de id alheio, agregações, export/import, e 401 em todas as rotas) e dois na migração (adoção do banco single-user e o caso ambíguo); no front, testes do store do token, do header `Authorization`, do 401 derrubando a sessão, das mensagens de erro de login/registro, da tela de autenticação e do novo botão de export. Orçamentos e metas continuam globais — é a próxima fatia.

- **2026-09-13** — Autenticação: registro e login com senha em argon2id e token JWT. Novo módulo `auth` no mesmo desenho dos outros (rotas → repositório, Zod na borda) e a migração 5 cria a tabela `users` com `email UNIQUE COLLATE NOCASE` — a primeira migração que entra pelo runner novo. Rotas: POST `/api/auth/register` (201 com `{ user, token }`, 409 se o e-mail já existe), POST `/api/auth/login` (200 ou 401) e GET `/api/auth/me` (devolve o dono do token). O token é assinado com `@fastify/jwt` (HS256, validade de 7 dias, `sub` = id do usuário) e a verificação ficou num preHandler `authenticate` reutilizável, que é o que a próxima fatia (multiusuário) vai pendurar nas rotas de transações. Decisões que valem explicar: (1) **argon2id** em vez de bcrypt, porque além de lento ele gasta memória (64 MiB por hash), o que encarece ataque com GPU — e o salt vem embutido no hash, sem coluna extra; (2) e-mail é **normalizado** (trim + minúsculas) no Zod, então "Lucas@Example.com" e "lucas@example.com" são a mesma conta; (3) duplicidade é resolvida pelo **UNIQUE do banco**, não por um SELECT antes do INSERT, então dois cadastros simultâneos não passam os dois; (4) login com senha errada e com e-mail inexistente devolvem **exatamente o mesmo 401** e, no caso do e-mail inexistente, o server ainda roda um `argon2.verify` contra um hash fictício — sem isso, a resposta mais rápida denunciaria quais e-mails têm conta; (5) a regra de "mínimo 8 caracteres" só vale no cadastro, e há teto de 128 para uma senha gigante não virar custo de CPU; (6) `JWT_SECRET` vem do ambiente e o boot **falha em produção** se ele não estiver definido — o segredo padrão só existe para dev e testes. Onze testes novos: token emitido sem vazar senha, normalização e 409 com outra caixa, validações, hash `$argon2id$` gravado no banco (abrindo o arquivo SQLite direto), login ok, 401 idêntico nos dois casos de falha, `/me` com token do cadastro e do login, e recusa de token ausente, adulterado, assinado com outro segredo ou de usuário inexistente.

- **2026-09-12** — Migrações versionadas no lugar do `CREATE TABLE IF NOT EXISTS` solto. Novo `db/migrations.ts` com uma lista ordenada de passos (`id`, `name`, `up`) na ordem histórica do schema — transações, coluna `recurring`, orçamentos, metas — e um runner próprio que cria a tabela `schema_migrations`, lê o que já rodou e aplica só o que falta, devolvendo os nomes aplicados (o boot loga quando aplica algo). Três decisões que valem explicar: (1) cada migração roda **dentro de uma transação junto com o próprio registro** — se o passo falhar no meio, o SQLite desfaz o DDL e a migração continua pendente, em vez de deixar o banco meio migrado e marcado como pronto; (2) os passos continuam **idempotentes** (`IF NOT EXISTS`, `ALTER` guardado por PRAGMA) porque os bancos que já existem em disco têm as tabelas mas não têm a tabela de controle — na primeira subida eles são "adotados", re-executando passos inofensivos só para ficarem registrados, sem perder dado; (3) o runner **valida a lista no boot** e recusa id repetido ou fora de ordem, que é o erro clássico de dois branches criando a mesma versão. O `openDatabase` ganhou um callback opcional `onMigrated` — e aqui apareceu uma pegadinha real: escrito como `options.onMigrated?.(runMigrations(db))`, o argumento **não é avaliado** quando o callback é omitido (o `?.()` curto-circuita a chamada inteira), então o banco subia sem schema; a chamada ficou em linha separada, com comentário. Sete testes novos cobrindo banco novo, segunda execução sem reaplicar, migração nova acrescentada depois, banco legado adotado com os dados preservados, rollback quando um passo falha e a validação de ordem. Isso é o pré-requisito das próximas fatias (auth e multiusuário), que vão precisar de `ALTER TABLE` em banco com dado dentro.

- **2026-09-11** — Import CSV das transações, fechando o ciclo do export. Nova rota POST `/api/transactions/import` que recebe o arquivo como corpo `text/csv` — o front lê o arquivo com `file.text()` e envia o texto, então não precisei de multipart nem de arquivo temporário no server (o limite de 1 MB do Fastify segura o tamanho). O formato aceito é exatamente o do export (`;`, vírgula decimal, BOM opcional), então dá para exportar, editar no Excel e importar de volta. O parser é próprio, RFC 4180, e conta linhas físicas: um campo entre aspas com quebra de linha não bagunça o número da linha no relatório. A validação é linha a linha e **não para no primeiro erro**: tipo (`receita`/`despesa`), valor em reais convertido para centavos por aritmética inteira (sem float), `recorrente` (`sim`/`não`) e o resto reaproveita o mesmo schema Zod do POST, com o nome do campo traduzido para a coluna do CSV. Decisão principal: **tudo ou nada** — se qualquer linha tiver erro, nada é importado e a API devolve 400 com `{ line, column, message }` de cada problema (as 50 primeiras + o total); se estiver tudo certo, as inserções rodam numa única transação do SQLite. Assim corrigir o arquivo e reenviar nunca duplica o que já tinha entrado. Na UI, botão "Importar CSV" ao lado do export, mostrando quantas transações entraram ou a lista de erros por linha; de quebra, a invalidação de cache repetida em quatro mutações virou um helper só. Sete testes novos no server (importação refletida em lista e resumo, round-trip com o próprio export, relatório completo sem importar nada, linha física com quebra dentro de aspas, cabeçalho/arquivo vazio/aspas abertas, relatório truncado, content-type) e quatro de componente.

- **2026-09-10** — Export CSV das transações do mês.
